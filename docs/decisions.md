# Proposed changes to the mapping

This is the list of changes proposed for [step 2 of the roadmap](roadmap.md#2-decide-what-to-change): each entry
names the [mapping](mapping/README.md) rule it changes, what it renders today, what other generators do, the
measured impact on openai-client-base, langfuse-client-base and their ergonomic crates, the options, and a
recommendation. Nothing here is implemented.

**Status: decided** (2026-11-09). All adopted entries ship together in one breaking release of the generator,
with the client changes in the same round; see [Release](#release).

The maintainer decides each entry separately. A decision is recorded by replacing `open` on its **Decision** line
(and in the table) with `adopt`, `adopt as option <name>`, or `keep`, with a short reason and the date. An adopted
entry then becomes a rule change in the mapping, and is implemented under [step 3](roadmap.md#3-make-the-generator-conform).

## 1. Response functions returning `ApiResponse<T>`

**Rule:** [`response.content.json`](mapping/response.md#responsecontentjson). Design A of
[decoding only what is needed, and ownership](design/partial-decoding-and-ownership.md#a-a-response-function-that-hands-out-the-body-recommended).

**Today:** a function decodes the whole body into the generated type and returns only that value. Status and headers
of a success are lost.

**Others:**
- stock: returns `T`; with `supportMultipleResponses` a `ResponseContent<Success>` (status, body text, entity), no
  headers. timvw-rust has the same option.
- progenitor: every method returns `ResponseValue<T>` with `status()`, `headers()` and `into_inner()`
  (progenitor-client `ResponseValue`).
- oapi-codegen: `ClientWithResponses` returns a `<Op>Response` struct with `Body []byte`, `HTTPResponse` and a typed
  field per status (`JSON200`, `JSON400`).

**Impact:**
- openai-client-base: 417 functions (360 operations plus the `contentTypeMethods` variants) would each get a
  `_response` twin; langfuse-client-base 135.
- No existing function changes, so nothing breaks.
- langfuse-ergonomic sends two requests itself instead of calling the generated function, to read headers:
  `src/batcher.rs` (ingestion: `x-request-id`, `Retry-After`) and `src/client.rs` (credential check: `x-request-id`).
  The ingestion case also needs the headers of an error status (429), which A alone does not give; see 4.

**Options:** adopt as option `responseFunctions` (off by default, no break); adopt always (doubles the API surface for
every spec); keep.

**Recommendation:** adopt as option `responseFunctions`: it gives subsets, borrowing and headers for any spec without
changing an existing function.

**Decision:** adopt as option `responseFunctions` (2026-11-09). Documented in full: a mapping rule, a usage guide with examples (the generated type, a subset, a borrowed subset, headers, errors) and the README option entry. Implemented in #70.

## 2. Request bodies by reference

**Rule:** [`requestBody.content.json`](mapping/request-body.md#requestbodycontentjson). Design C of
[decoding only what is needed, and ownership](design/partial-decoding-and-ownership.md#c-request-bodies-by-reference).

**Today:** `create_item(configuration, item: models::Item)`; the function only serializes it (`.json(&p_body_item)`).

**Others:**
- stock: by value (`req_builder.json(&param)` on an owned argument), the same as today.
- progenitor: the positional interface takes `&'a types::Item` (typify's `parameter_ident_with_lifetime`: every
  struct, newtype, `Vec` and map is passed by reference); the builder interface takes `TryInto<types::Item>` by value.

**Impact:**
- Generated functions with a JSON body argument: openai-client-base 154 of 417, langfuse-client-base 44 of 135.
- Call sites passing a body: openai-ergonomic 20 in `src/` (19 `.<body>(request)` builder calls and one
  `.maybe_create_thread_request(Some(request))`) and 7 in `examples/`; langfuse-ergonomic 7 in `src/`. Each becomes
  `&request`.
- Neither ergonomic crate clones a request to keep it (no `request.clone()` before a call), so neither gains anything
  today.

**Options:** adopt as option `borrowedRequestBodies` (bon builders get a lifetime); adopt always (breaking for every
caller); keep.

**Recommendation:** adopt as option `borrowedRequestBodies`, left off in both clients until a caller needs it: it is
cheap to offer, but today the edit buys the two clients nothing.

**Decision:** adopt, always, with no option (2026-11-09). A function that only serializes its body borrows it (`&models::Item`), as the Rust API guidelines advise; the clients' call sites change in the same release. Implemented in #65.

## 3. Cookie parameters are not sent

**Rule:** [`parameter.in.cookie`](mapping/parameter.md#parameterincookie).

**Today:** the parameter is a function argument that the function never uses.

**Others:**
- stock: the same; the `reqwest` `api.mustache` has no cookie section.
- progenitor: generation fails, `cookie parameters are not supported` (`progenitor-impl` `method.rs`).
- oapi-codegen: not verified.

**Impact:** no cookie parameters in either spec (0 of 720 parameters in openai, 0 of 220 in langfuse), so neither
client changes.

**Options:** adopt: send the operation's cookie parameters as one `Cookie` header, `name=value` pairs joined with
`; `, a `None` left out (the signature stays as it is); fail generation instead; keep.

**Recommendation:** adopt: the argument already exists and silently dropping it is a bug.

**Decision:** adopt (2026-11-09): the operation's cookie parameters that are set go out in one `Cookie` header, percent-encoded where the cookie syntax needs it. Implemented in #69.

## 4. Response headers cannot be read

**Rules:** [`header.schema`](mapping/header.md#headerschema), and the error side of
[`responses.statusCode`](mapping/responses.md#responsesstatuscode).

**Today:** a JSON or text success returns only the decoded body. An error status gives
`ResponseContent { status, content, entity }`, also without headers.

**Does 1 close it?** For successes, yes: `ApiResponse` has `headers`. For errors, no: 1 keeps the typed
`Error::ResponseError(ResponseContent)`, which has no headers. The headers that matter most (`Retry-After`,
`x-request-id`, rate limits) come with error statuses.

**Others:**
- stock: no headers on success or error (`api_mod.mustache`: `ResponseContent` has `status`, `content`, `entity`).
- progenitor: `Error::ErrorResponse(ResponseValue<E>)`, so an error has `headers()` too.
- oapi-codegen: `HTTPResponse` on every response, success or error.

**Impact:**
- Declared success headers: openai 2 operations (`Location`, `Transfer-Encoding`), langfuse none. Most headers that
  matter are not declared in the spec, so this is about the `HeaderMap` and not typed header fields.
- langfuse-ergonomic's `map_api_error` (`src/error.rs`) sets `request_id: None` and `retry_after: None` at 4 places
  because there are no headers, and `src/batcher.rs` skips the generated `ingestion_batch` to read them.
- Adding a public field to `ResponseContent` breaks code that builds one with a struct literal: one test in
  openai-ergonomic (`src/client/mod.rs`, `map_api_error_converts_response`), none in langfuse-ergonomic.

**Options:** add `headers: reqwest::header::HeaderMap` to `ResponseContent` (breaking only for struct literals);
the same as an option; keep (success headers through 1 only).

**Recommendation:** adopt the field, in a breaking generator release: one test line to fix, and it removes a reason
for langfuse-ergonomic to bypass the generated client.

**Decision:** adopt (2026-11-09): success headers through 1; `ResponseContent` gets `headers: reqwest::header::HeaderMap` for errors. Typed accessors for declared response headers are out of scope. Implemented in #68.

**Decision (2026-11-09, follow-up):** errors are always boxed; `boxResponseError` removed. With `headers` an unboxed
`ResponseContent` puts every function over clippy's `result_large_err` limit, so `Error::ResponseError` always holds
`Box<ResponseContent<T>>`, and setting `boxResponseError` fails generation as not configurable. Implemented in #68.

## 5. Error variant chosen by body shape, not status

**Rule:** [`responses.statusCode`](mapping/responses.md#responsesstatuscode).

**Today:** the error body is decoded into the `#[serde(untagged)]` enum, so the first variant whose type accepts it
wins. A 404 whose type is the same as the 400's comes back as `Status400`.

**Others:**
- stock: the same (`serde_json::from_str(&content).ok()` into the untagged enum).
- progenitor: matches on the status code (`400u16 => ...`, ranges as `400..=499`, `default` as `_`); it requires one
  error type for all error responses of an operation (`assert!(response_types.len() <= 1)`).
- oapi-codegen: one typed field per status (`JSON400`, `JSON404`), filled by status.

**Impact:**
- openai: 307 of 360 operations have two or more error statuses with the same body schema (mostly `ErrorResponse`);
  for those every such error decodes as the first (`Status400`). langfuse: all 120 operations, every error is
  `Status400(serde_json::Value)`.
- Neither ergonomic crate reads `entity` or a `Status…` variant: both map errors by `status` and `content` only.
- The enum type stays the same; the variant a caller gets changes. No compile break.

**Options:** adopt: decode into the variant of the matching status (exact code, then `4XX`-style range, then
`default`), and `UnknownValue` when that variant does not decode; adopt as an option; keep.

**Recommendation:** adopt: the variant names promise a status, and no caller of the two clients depends on the
wrong one.

**Decision:** adopt (2026-11-09): the generated code matches the status code first and decodes the body as that status's type; an unlisted status falls back to `DefaultResponse`, a body that does not decode to `UnknownValue`. Implemented in #64.

## 6. `uuid` parameters are `&str`

**Rule:** [`schema.format.uuid`](mapping/schema.md#schemaformatuuid).

**Today:** `uuid::Uuid` in a model, `&str` as a path, query or header parameter.

**Others:**
- stock: the same (`api.mustache` renders `isUuid` parameters as `&str`).
- progenitor: typify maps `format: uuid` to `::uuid::Uuid` everywhere; a parameter is `&'a uuid::Uuid`.

**Impact:** neither spec has `format: uuid` anywhere (0 parameters, 0 schemas).

**Options:** adopt: `uuid::Uuid` (or `Option<uuid::Uuid>`), sent with its `Display`; adopt as an option; keep.

**Recommendation:** adopt: it makes models and parameters agree, and costs the two clients nothing.

**Decision:** adopt, with no option (2026-11-09). The mapping records the rule behind it: a format has one Rust type wherever it appears (model, parameter, body); its crate is a dependency only when the API uses the format; a fallback to `String` exists only where a user needs it (`useChrono`). `uri`, `email` and `decimal` stay `String`. Implemented in #66.

## 7. `readOnly` and `writeOnly` in both directions

**Rule:** [`schema.readOnly`](mapping/schema.md#schemareadonly).

**Today:** an ordinary field both ways; a required read-only field must be given to `new()` and is sent.

**Others:**
- stock: ignored (no `readOnly` in `model.mustache`).
- progenitor: passes the flags to schemars metadata, but typify does not use them (no `read_only` in typify-impl), so
  ignored.

**Impact:** openai has one `writeOnly` property (`LiveSIPTrunkAuth.password`, required), in a request-only schema
(the spec says the response does not return it), and no `readOnly`; langfuse has neither. Nothing decodes or sends
wrongly today.

**Options:** adopt as option `readWriteOnly`: a read-only field leaves `new()` and the builder and is not serialized;
a write-only field is optional when decoding. Separate request and response types (larger change). Keep.

**Recommendation:** keep: neither spec has a case where it matters, and no other Rust generator does it.

**Decision:** keep (2026-11-09): `readOnly` and `writeOnly` stay ignored.

## 8. `uniqueItems` is a `Vec`

**Rule:** [`schema.uniqueItems`](mapping/schema.md#schemauniqueitems).

**Today:** `Vec<T>`.

**Others:**
- stock: `Vec<T>`.
- progenitor: typify recognizes `uniqueItems: true` as a set, but renders it as `Vec` (`// TODO we'll want this to be
  a Set of some kind`).

**Impact:** neither spec uses `uniqueItems`.

**Options:** adopt: `BTreeSet<T>` (needs `Ord` on the item, which models with `f64` or `serde_json::Value` lack);
keep.

**Recommendation:** keep: no client uses it and a set type does not work for every item type.

**Decision:** keep `Vec` (2026-11-09); the generated `validate()` of 9 reports duplicates (by equality, so any item type works). Implemented in #67.

## 9. Validation keywords are not checked

**Rule:** [`schema.pattern`](mapping/schema.md#schemapattern).

**Today:** `pattern`, `minLength`, `maximum`, `minItems`, ... change nothing.

**Others:**
- stock: not checked (no validation in the Rust templates).
- progenitor: typify renders a string with `minLength`, `maxLength` or `pattern` as a newtype that checks them when
  built and when deserialized; integer bounds choose the integer type (`u8`, `NonZeroU64`, ...); `minItems` and
  `maxItems` are not enforced (`// TODO enforce size limitations`). Number bounds: not verified.

**Impact:** openai uses them a lot (720 `minLength`, 421 `maxLength`, 204 `minimum`, 146 `maximum`, 180 `minItems`,
190 `maxItems`, 30 `pattern`, 35 `minProperties`, 26 `maxProperties`, 7 `exclusiveMinimum`); langfuse not at all.
Checking when decoding would reject responses the server sends whenever the spec's bounds lag the API; typify-style
newtypes would change the type of every openai field with `minLength`, `maxLength` or `pattern`.

**Options:** adopt (checked newtypes, breaking); adopt as option: a generated `validate()` per model, called by the
caller, no type change; keep.

**Recommendation:** keep: the server checks anyway, and decode-time checks would make openai-client-base fail on
responses it decodes today. Revisit `validate()` if a caller asks.

**Decision:** adopt (2026-11-09): every model implements a generated `Validate` trait (`fn validate(&self) -> Result<(), ValidationError>`), also models without constraints of their own, which check their nested models. It checks string length and `pattern` (with `regex`, a dependency only when a spec has a pattern; a pattern `regex` cannot express is skipped with a generation warning), number bounds and `multipleOf`, item counts and `uniqueItems`, recursively. Generated functions never call it: validating is the caller's choice, so a spec stricter than its server never blocks a request, and `Error` gets no new variant. Generated by default; an option turns the generation off. Constraints are also written in the field's documentation. Implemented in #67.

## 10. Unknown generator options are ignored

**Rule:** none; the options are listed in the [README](../README.md#configuration).

**Today:** openapi-generator keeps every `--additional-properties` key (and every key of a `-c` file) in a free-form
map. timvw-rust reads the keys it knows and rejects the stock ones it does not support, but a misspelt key
(`boxOnlyCycle`) is ignored and the output silently differs. Since timvw-rust rejects custom templates (`-t`), no
template can read an extra key, so an unknown key can only be a mistake.

**Others:**
- stock: ignored; openapi-generator does not check additional properties against a generator's options.
- progenitor: settings are a Rust struct (`GenerationSettings`) and clap flags for `cargo progenitor`, so an unknown
  setting does not compile or is a command-line error.

**Impact:** every key both clients pass is a timvw-rust option (openai: 30 keys in `generator-config.json`; langfuse:
15 `--additional-properties` in `generate-openapi-client.sh`). One finding: `boxOnlyCycles` is read but not
registered as a CLI option, so `config-help` does not list it and an allow-list built from the CLI options alone
would reject a key both clients set. It has to be registered first.

**Options:** adopt: fail generation on a key that is neither a timvw-rust option, nor one of openapi-generator's
global options (those of `DefaultCodegen`, which timvw-rust removes from its own `cliOptions`), nor a key
openapi-generator puts in the map itself before `processOpts` (which ones exactly is to be taken from a run: not
verified); the message names the closest known option ("did you mean `boxOnlyCycles`?"). Adopt as a warning. Keep.

**Recommendation:** adopt as an error: it is the same reasoning as rejecting stock options, and it breaks no client.

**Decision:** adopt (2026-11-09): an unknown option fails generation and names the closest known option. The allow-list holds the generator's options, openapi-generator's general options and the keys it sets itself (taken from a run). `boxOnlyCycles` is registered as an option first. Implemented in #62.

## 11. `date-time` parameters are sent in `Display` form

**Rules:** [`schema.format.date-time`](mapping/schema.md#schemaformatdate-time),
[`parameter.in.query`](mapping/parameter.md#parameterinquery). Found by comparing; not yet a documented gap.

**Today:** with `useChrono` (the default) a `date-time` parameter is `chrono::DateTime<chrono::FixedOffset>` and is
sent as `param_value.to_string()`. chrono's `Display` writes `2026-01-01 00:00:00 +00:00`, not RFC 3339
(`2026-01-01T00:00:00+00:00`), which `format: date-time` requires. Bodies are fine: serde writes RFC 3339.

**Others:**
- stock: the same (`.to_string()` on every query parameter).
- progenitor: query parameters go through `progenitor_client::QueryParam`, which serializes the value with serde, so
  RFC 3339. Path parameters: not verified.

**Impact:** langfuse-client-base has 29 `date-time` query parameters in 15 functions (`trace_list`,
`observations_get_many`, `scores_get_many`, ...). langfuse-ergonomic's `list_traces` (`src/traces.rs`) builds the
request by hand for this reason ("formats date query parameters with Display, which inserts spaces instead of the
RFC3339 `T`"). openai-client-base sets `useChrono=false`, so its date parameters are strings and unaffected. The
signatures stay the same, so nothing breaks.

**Options:** adopt: send `to_rfc3339()` for `date-time` (and keep `Display` for `date`, which is already
`YYYY-MM-DD`) in path, query and header parameters; keep.

**Recommendation:** adopt: it is a wire bug, and fixing it lets langfuse-ergonomic call the generated `trace_list`.

**Decision:** adopt (2026-11-09): `date-time` parameters are sent with `to_rfc3339()`, `date` parameters as `YYYY-MM-DD`, in path, query and header. Implemented in #63, which also covers form fields (urlencoded and multipart text parts).

## 12. Option defaults are stock, not the baseline

**Rule:** the [baseline](mapping/README.md#what-the-generator-renders): the mapping's **Rust** entries describe the rendering with 11
options on, but each of them defaults to off, which renders what stock `-g rust` renders.

**Today:** a new user who passes no options gets the stock renderings the
[comparison](comparison/README.md#summary) found wrong: discriminated unions that decode no message, `i32` for
integers without a format, closed enums that fail on a new value, `Default` on every struct.

**Others:** not applicable; the defaults exist to stay compatible with configurations taken over from `-g rust`.

**Impact:** none on the clients: both set all 11 baseline options explicitly (openai in `generator-config.json`,
langfuse in `generate-openapi-client.sh`). For any other user it is a breaking change of the output.

**Options:** adopt: the baseline options default to on, and each can still be turned off; adopt for new options only;
keep.

**Recommendation:** adopt in a breaking generator release: the documented mapping should be what the generator renders
without options.

**Decision:** adopt, further than recommended (2026-11-09): the 11 baseline options are removed and their behaviour is always applied; setting one fails generation as "not configurable", like the fixed stock options. `false` gave no rendering worth keeping: boxing every reference, `Default` where invalid, no `FromStr`, a JSON `Display` on structs, `i32` that overflows, ambiguous inline names, the stock unions, unions that ignore their tag, response enums that fail on a new value (request enums stay closed), no default in the docs, and nullable unions that cannot send `null`. The clients remove the 11 lines in the same release; their output does not change. Implemented in #61.

## Release

Every adopted entry (1–6 and 8–12) ships in one breaking release of the generator, implemented under
[step 3](roadmap.md#3-make-the-generator-conform), one change at a time with its mapping rule and tests. Before the
release, each change is checked against both clients. openai-client-base and langfuse-client-base then upgrade in the
same round: they remove the 11 baseline options from their configuration, and their ergonomic crates pass request
bodies by reference (2) and may use the response functions (1), the headers on errors (4) and `validate()` (9).
