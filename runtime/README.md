# timvw-rust-runtime

The runtime of Rust clients generated by [openapi-generator-timvw-rust](https://github.com/timvw/openapi-generator-timvw-rust)
(`-g timvw-rust`, the default `httpStack=tower`). A generated client sends every request through a `Client`: a
[tower](https://docs.rs/tower) service from `http::Request<Body>` to `http::Response<Body>`.

- By default the service is [reqwest](https://docs.rs/reqwest) (feature `reqwest`, with `rustls` or `native-tls`).
- `Client::layer` wraps it in any tower layer: retries, timeouts, rate limits, tracing.
- `Client::from_service` replaces it with any other service: a hyper client, or a mock in tests.

```rust,no_run
use std::time::Duration;
use timvw_rust_runtime::{retry::RetryPolicy, Client};

let client = Client::default()
    .layer(tower::timeout::TimeoutLayer::new(Duration::from_secs(30)))
    .layer(tower::retry::RetryLayer::new(RetryPolicy::default()));

// A generated client takes it in its configuration:
// let mut configuration = my_client::apis::configuration::Configuration::new();
// configuration.client = client;
```

Layers apply from the inside out: the last one added sees a request first. In the example a retry gets a fresh 30 s
timeout.

## Features

| Feature | Default | What it adds |
| --- | --- | --- |
| `reqwest` | via `rustls` | `ReqwestService`, and `Client::default()` sends with reqwest |
| `rustls` | yes | `reqwest` with rustls |
| `native-tls` | no | `reqwest` with the platform's TLS |
| `retry` | yes | `retry::RetryPolicy` for `tower::retry::RetryLayer` (sleeps with tokio) |

Without `reqwest`, `Client::default()` fails every request; set a service with `Client::from_service`.

## What the generated code uses

The generated functions build requests with `RequestBuilder` (`query`, `header`, `bearer_auth`, `basic_auth`, `json`,
`form`, `body`, `multipart`, `build`) and read them with `Response` (`status`, `headers`, `text`, `bytes`,
`bytes_stream`): the same methods as reqwest, so the generated code reads the same as with reqwest. Multipart bodies
are encoded by `multipart::Form`; a form held in memory (every part bytes or text) can be sent again by a retry
layer, a form with a streamed part cannot.

## Retries

`retry::RetryPolicy` retries `429`, `408` and `5xx` responses and failures to connect, at most three times by default.
It waits as long as `Retry-After` (seconds) asks, or backs off exponentially from 200 ms, capped at 8 s. A request with
a streamed body (a streamed file upload) is not retried, since it cannot be sent again.
