# Header Object

Rules for the [Header Object](https://spec.openapis.org/oas/v3.0.3#header-object).

Tests are in `src/test/java/be/timvw/openapi/rust/`; a test is named `Class#method`. `OtherObjectsTest` renders
`src/test/resources/other_objects.yaml` without options.

### `header.schema`

| | |
| --- | --- |
| OpenAPI | `headers` of a response |
| Rust | no typed header fields (with `responseFunctions`, a success's declared headers are typed: [`header.schema.typed`](#headerschematyped)). An error response's `ResponseContent` has `headers: reqwest::header::HeaderMap`, every header of the response, declared or not (see [`responses.statusCode`](responses.md#responsesstatuscode)). `{:?}` of such an error prints every header, which can include `set-cookie` or tokens; its `Display` does not print them. A JSON or text success returns only its decoded body, except with `supportMultipleResponses`, whose success `ResponseContent` has the `headers` too. A binary response returns the whole `reqwest::Response`, whose headers the caller can read |
| Library | `reqwest::header::HeaderMap` |
| Options | `supportMultipleResponses`: the success `ResponseContent` has `headers` as well. `responseFunctions`: `<operation>_response` returns the headers of a success in its `ApiResponse` ([`response.content.response-function`](response.md#responsecontentresponse-function)), and the headers its successes declare are typed ([`header.schema.typed`](#headerschematyped)) |
| Gap | the headers of a JSON or text success cannot be read without `supportMultipleResponses` or `responseFunctions` |
| Tests | [`OtherObjectsTest#declaredResponseHeadersGetNoTypedAccessorWithoutResponseFunctions`](../../src/test/java/be/timvw/openapi/rust/OtherObjectsTest.java#L76), [`ErrorStatusTest#whatItDecodesAtRunTime`](../../src/test/java/be/timvw/openapi/rust/ErrorStatusTest.java#L165) |

### `header.schema.typed`

| | |
| --- | --- |
| OpenAPI | `headers` of an operation's success responses (`2xx`, `3xx`, exact or a range; the `default` response when the operation has neither), inline, a `$ref` to `components/headers`, or in a `$ref`'d `components/responses` entry |
| Rust | with `responseFunctions`, a struct `<OperationId>ResponseHeaders` in the API module, next to `<OperationId>Error`, with a field `Option<T>` per declared header, `#[derive(Clone, Debug, Default, PartialEq)]`. The field is the header name in lower case, named as a property is (`X-RateLimit-Remaining-Images` is `x_ratelimit_remaining_images`, `type` is `r#type`); two headers that become the same field get `_2`, `_3`, ... in the order the spec lists them (with a warning); a name that is not an HTTP token (a space, a quote, a non-ASCII letter) gets no field (with a warning). The field's documentation gives the header as the spec spells it (`ETag`). `T` is the type a parameter of the header's `schema` (or its `content`'s schema) has: `i64` (`i32` for `int32`), `f64` (`f32` for `float`), `bool`, `String`, `uuid::Uuid`, `chrono::DateTime<chrono::FixedOffset>` and `chrono::NaiveDate` (`String` with `useChrono=false`), an enum component (`models::Status`), or a `Vec` of one of those for an array. An inline enum is `String`, as a parameter of one is without `typedEnumParameters`; a header with `content` instead of `schema` takes its first media type's schema but is read as plain text (a JSON `content` is not decoded: a JSON string keeps its quotes and fails to parse as anything but `String`); a schema without a text form (an object, a map, a union, a free-form value, an array of arrays) is the header's text, `String`. The struct holds the headers of every success: one declared by only some statuses is an `Option` like the others, and one declared with different types is `String`. `<OperationId>ResponseHeaders::from_headers(&HeaderMap)` and `From<&HeaderMap>` read it from any header map, and `ApiResponse::typed_headers::<<OperationId>ResponseHeaders>()` from the response of a `_response` function, whose documentation names the struct; the methods of `contentTypeMethods` share the operation's struct. No struct for a header no success declares (an error status's), for an operation without a `_response` function (a binary or event-stream response, a webhook), or without the option; a crate without any struct renders as before |
| Wire | the header is looked up ignoring case; its first value, trimmed, is parsed: an integer, a number or a `uuid` with Rust's `FromStr`, a `bool` from `true`/`false`, a `date-time` as RFC 3339, a `date` as `YYYY-MM-DD`, an enum as its JSON value (`"done"`, `2`): a value the enum does not list is `Some(Unknown)` for an open enum (one a response body can hold, see [`schema.enum.open`](schema.md#schemaenumopen)) and `None` for a closed one (an enum only headers use). An array is a comma-separated list (the `simple` style) over every occurrence of the header, items trimmed and empty ones skipped. A header that is missing, not UTF-8 or does not parse (one item of a list included) is `None`, never an error. A `String` is the first value trimmed of surrounding whitespace, so an empty value is `Some("")` |
| Library | `reqwest::header::HeaderMap` |
| Options | `responseFunctions`, off by default. Skipped, as they describe the connection and not the response: the hop-by-hop headers `Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Transfer-Encoding` and `Upgrade` (RFC 9110, section 7.6.1), and `Content-Type`, which the OpenAPI specification says a response's `headers` ignore. Stock has no typed headers. See the [guide](../guides/response-functions.md#declared-headers-typed) |
